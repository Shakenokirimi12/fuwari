# DAZN の解約フローから学ぶ UI ダークパターン全 6 種

## はじめに

先日、ブログ『ゲムぼく。』さんの「[検証：DAZN（ダゾーン）は何クリックで解約できるのか？](https://gameboku.com/archives/26073016.html)」という記事が話題になっていました。

結論から言うと、**16 クリック・13 画面・6 つの罠**、そして**解約完了後さらに 30 日ぶんの支払い**が必要だったそうです。

わたしは笑いました。そのあと真顔になりました。**これ、誰かが実装したんですよね。**

コンポーネントを切って、状態遷移を設計して、ボタンの `variant` を決めて、PR を出して、レビューが通って、デプロイされている。そういう工程を経てこの世に出ている。つまりこれは、**エンジニアリングの成果物**なんです。

というわけでこの記事では、この解約フローを「怒りの対象」ではなく「**教材**」として扱います。ダークパターンの標準的な分類にマッピングしながら、「じゃあどう実装すべきだったのか」を毎回セットで考えていきます。

なお、わたしは DAZN の中の人ではないので、以下の実装コードはすべて**わたしの想像**です。想像なんですが、たぶんそんなに外れてないと思います。そこが一番こわい。

---

## そもそもダークパターンとは

UX デザイナーの Harry Brignull が 2010 年に提唱した概念で、「**ユーザーが意図していない行動を取らせるために意図的に設計された UI**」のことです。本人は現在「deceptive patterns（欺瞞的パターン）」という呼称を推しています。「dark」に人種的な含みがあるという指摘を受けての改称です。

重要なのは「**意図的に**」の部分です。使いにくいだけの UI はダークパターンではありません。それはただの**バグ**か、**予算**です。

ダークパターンは、使いにくさが**機能している**。押し間違えたときに得をするのが企業側で、損をするのがユーザー側。この非対称性が成立していたら、それはもうダークパターンです。

判定式はシンプルです。

```ts
const isDarkPattern = (ui: UI): boolean =>
  ui.userMistakeRate > 0 && ui.beneficiaryOfMistake === "company";
```

`userMistakeRate` が高いのに誰も直さない機能があったら、それはバグではなく**仕様**です。悲しいね。

## 罠 その 1：Low Visual Prominence（視覚的劣後）

> [4] プラン詳細画面から、いろいろ書いてある情報をすべて無視して最下部に極小フォントで書いてある「プランを解約」を見つけて押す。罠。

### 何が起きているか

解約導線が**極小フォントで最下部**に置かれています。リンクは存在する。存在するので「解約できないわけではない」と言い張れる。でも見つからない。

これは Low Visual Prominence、あるいは Visual Interference と呼ばれるパターンです。**削除するのではなく、視認性を下げる**。技術的には何も嘘をついていないのがポイントで、法務レビューを通しやすい。だから蔓延する。

### たぶんこういう実装

```tsx
// 継続してほしい導線
<Button variant="primary" size="lg" fullWidth>
  プランを変更する
</Button>

// 解約導線
<a
  href="/cancel"
  className="text-[10px] text-gray-400 underline-offset-4"
>
  プランを解約
</a>
```

`text-gray-400` に `text-[10px]`。背景が白なら**コントラスト比はだいたい 2.8:1** です。WCAG 2.1 の AA 基準は通常テキストで 4.5:1。つまり**アクセシビリティ基準を堂々と割っている**。

ここで大事なのは、これが「うっかり」ではまず起きないということです。`text-sm text-gray-600` あたりがデフォルトのデザインシステムを使っていて、そこから**わざわざ 2 段階下げている**。誰かが Figma で数値を打ち込んで、誰かがそれをコードに落として、誰かが approve している。**チーム戦**です。強い。

### どうすれば良かったか

**同じ階層の操作は、同じ視覚的重みで置く。** これだけです。

```tsx
// 契約に関する操作はすべて同じ粒度で並べる
<ActionList>
  <ActionListItem to="/plan/change">プランを変更</ActionListItem>
  <ActionListItem to="/payment">支払い方法を変更</ActionListItem>
  <ActionListItem to="/cancel">プランを解約</ActionListItem>
</ActionList>
```

`variant` を変えたくなったら、自分に聞いてください。「**これはユーザーのための強調か？ 会社のための強調か？**」

前者なら通していい。破壊的操作を `danger` にするのはユーザーのための強調です。後者なら、それは強調ではなく**誘導**です。名前を正しく呼ぶだけで、だいぶ判断が楽になります。

ついでに言うと、これは Lint できます。

```js
// eslint-plugin-a11y-contrast みたいな
// 「本文サイズが 12px 未満 かつ コントラスト比 4.5 未満」を error に
```

CI で落ちるようにしておけば、少なくとも「気づかずにやってしまった」は撲滅できます。「気づいてやっている」ほうは……まあ、CI では止められません。あれは人間の問題です。

## 罠 その 2：Interface Interference（色の反転）

ここが一番おもしろい罠です。

> [5]〜[8] 「解約を進める」（黒いボタン）を押す。
> [9] すっかり慣れた黒いボタンではなく、いままでハズレだった白いボタン（今回は見送る）を押す。**急にひっくり返ったな。オセロか？**

### 何が起きているか

4 画面連続で「**黒 = 解約を進む**」を学習させたあと、**5 画面目でいきなり色の意味を反転させる**。

これは認知科学的に見ると、かなり悪質です。人間はインターフェースを 3 回も繰り返せば手続き記憶（procedural memory）に落とし込みます。つまり **5 回目はもう画面を読んでいない**。読まなくても押せるように学習させたのは UI 側なのに、そこで裏切る。

しかもこの画面、間違えて黒を押すと**解約されないどころか年間プランにアップグレードされる**そうです。

解約しにきて年契約になる。**RPG でセーブしようとしたらセーブデータが消えるどころかハードモードで最初から始まる**みたいなことが起きている。

### たぶんこういう実装

```tsx
// CancelStep1〜4.tsx
<Button variant="primary">解約を進める</Button>
<Button variant="ghost">キャンセル</Button>

// RetentionOffer.tsx （担当チームが違う）
<Button variant="primary">年間プランで続ける</Button>  {/* 黒 */}
<Button variant="ghost">今回は見送る</Button>          {/* 白 */}
```

**注目すべきは、コードとしては両方とも正しいということです。**

どちらの画面も「主要導線を `primary`、副次導線を `ghost`」という、**まったく正しいデザインシステムの使い方**をしている。ファイル単体でレビューしたら、誰も何も指摘できない。

問題は「主要導線とは誰にとっての主要導線か」の定義が、画面 4 と画面 5 のあいだで**サイレントに切り替わっている**ことです。画面 4 までは「ユーザーの目的」が primary で、画面 5 からは「事業の目的」が primary になっている。

これは十中八九、**解約フローチームとリテンションチームが別**です。リテンション画面は CVR で KPI を持っていて、A/B テストを回して、「黒のほうが押される」という有意差を出して、勝ってしまった。悪意なくダークパターンが生まれる典型的な経路がこれです。**A/B テストは、ダークパターンの自動生成装置になりうる。**

### どうすれば良かったか

**ボタンの色は「重要度」ではなく「意味」に紐付ける。** そしてそれをフロー単位で固定する。

```tsx
// ❌ 見た目の階層で決める
<Button variant="primary">
<Button variant="secondary">

// ✅ 意味で決める。色は semantic トークンが解決する
<Button intent="proceed">解約を進める</Button>
<Button intent="abort">解約をやめる</Button>
```

`intent="proceed"` は**フロー全体で必ず同じ見た目**になる。これを型で縛ります。

```ts
type FlowIntent = "proceed" | "abort";

// フロー内のボタンは intent 必須、variant 直指定は禁止
type FlowButtonProps = {
  intent: FlowIntent;
  children: ReactNode;
};
```

こうしておくと、画面 5 で色を反転させたい人は「`intent` の定義そのものを変える」しかなくなります。そして `intent` の定義を変えると**全画面が一斉に反転する**ので、レビューで一発でバレる。

**ダークパターンを「実装しにくく」しておくのが、設計でできる最大の防衛です。** 悪意を禁止するのは無理ですが、悪意にコストを払わせることはできる。

そして最後に、A/B テストのゴール設計についてひとこと。

「リテンション画面のクリック率」を最大化すると、**押し間違いも成果としてカウントされる**んですよね。押し間違えた人は 30 日後に返金を求めて CS に電話をかけてくるんですが、その電話は CS チームの KPI なので、リテンションチームのダッシュボードには**映らない**。

組織図がそのまま UI に染み出す。**コンウェイの法則、ダークパターン編**です。

## 罠 その 3：Trick Wording（二重否定）

> [10] 解約ではなく一時停止を促されるので、一時停止に「参加しない」を選択する。**「一時停止に参加しない」って「反対に賛成しない」みたいでめちゃめちゃややこしいな。**

### 何が起きているか

「一時停止」というネガティブな語に「参加しない」という否定がかかって、**二重否定**になっています。ユーザーは「解約したい」という単純な意図を、頭のなかで NOT を 2 回適用して選択肢に変換しなければならない。

しかもこの画面のボタンは黒。前段の学習と噛み合っていて、**認知負荷と学習の裏切りの合わせ技**になっています。

### どうすれば良かったか

**選択肢のラベルは、押した結果を主語つきの現在形で書く。**

```tsx
// ❌ 選択肢が状態への賛否になっている
<Button>一時停止に参加しない</Button>
<Button>一時停止に参加する</Button>

// ✅ 選択肢が結果そのものになっている
<Button>解約を続ける</Button>
<Button>解約せず、1か月休会する</Button>
```

判定基準を 1 つ挙げるなら、**ラベルに「ない」が入っていたら黄信号**です。ドキュメントの命名規則で `isNotDisabled` を禁止するのと同じ話で、これは UI 文言でも通用します。二重否定は、コードでもコピーでも読みにくい。

もうひとつ、実務でとても効く簡易テストがあります。

> そのボタンのラベルだけを、**画面から切り離して**声に出して読む。
> それだけで「押したら何が起きるか」がわからなければ、ラベルとして失格。

「一時停止に参加しない」。……**何？** はい失格。

## 罠 その 4：Sneaking / Hidden Costs（アディショナルタイム 30 日）

ここは笑えないやつです。

> [11] 次回請求日は 8 月 15 日なのだが、サブスクリプション終了日がしれっと **8 月 27 日に延長**されている。「即時解約」でも「現契約の満了をもって解約」でもなく、「**解約手続きを完了した日から 30 日後を実際の解約日とし、追加日数分は日割り請求**」だからである。**アディショナルタイムが長すぎる。不可避の罠。**

### 何が起きているか

**解約操作が、契約終了日を後ろに延ばしている。**

もう一度書きます。**解約すると、契約期間が伸びる。**

これは Sneaking（こっそり忍ばせる）＋ Hidden Costs（隠れた費用）の合わせ技です。しかも「不可避」なのが致命的で、他の 5 つの罠はユーザーが注意深ければ回避できますが、これだけは**どれだけ注意深くても回避できない**。UI の問題ではなく、**契約ロジックの問題**だからです。

### たぶんこういう実装

```ts
// 「30日前告知」条項をそのままコードに落とした結果
function cancelSubscription(sub: Subscription, now: Date) {
  const NOTICE_PERIOD_DAYS = 30;
  return {
    ...sub,
    endsAt: addDays(now, NOTICE_PERIOD_DAYS),
    status: "pending_cancellation",
  };
}
```

このコード、**単体では完全に正しい**んですよ。「解約には 30 日前の通知が必要」という契約条項を、素直に、忠実に実装している。テストも通る。レビューも通る。

エンジニアリングとしては 100 点です。問題は、**契約条項のほうが 0 点**だということ。

これがサブスクの解約 UI でいちばん厄介なところで、**バグではなく仕様なので、直すには実装者ではなく契約書に手を入れる必要がある**。エンジニアの手の届く範囲を超えている。届かないんだけど、実装したのはエンジニアなので、Xでバズったときに矢面に立つのはだいたい UI です。理不尽。

### どうすれば良かったか

**契約条項を変えられないなら、せめて「金額」を先に見せる。**

```tsx
<CancellationSummary>
  <Row label="解約手続き日" value="2026年7月30日" />
  <Row label="サービス終了日" value="2026年8月27日" emphasis />
  <Row label="このあと発生する請求" value="1,340円" emphasis />
  <Note>
    ご契約には30日前の通知期間があるため、
    次回請求日（8/15）以降も12日分の日割り料金が発生します。
  </Note>
</CancellationSummary>
```

**追加でいくら払うのかを、確定ボタンより前に、円で書く。**

これは倫理の話である以前に、**法律の話**です。日本の改正特定商取引法（2022 年 6 月施行）は、いわゆる「最終確認画面」で分量・金額・期間・解約条件を明示することを義務付けています。EU では 2024 年の Digital Fairness Fitness Check でダークパターンが名指しで問題視され、米国 FTC は 2025 年に「click-to-cancel」規則を打ち出しました（こちらは同年 7 月に連邦控訴裁で手続き上の理由により無効とされましたが、州法レベルでの規制は進行中です）。

**規制はダークパターンを追いかけている最中で、しかもだいぶ距離を詰めてきている。** 「今はグレーだからセーフ」で書いたコードは、**数年後に技術的負債どころか法的負債になる**ということです。

`// TODO: 法改正で直す` は、TODO コメントのなかで最悪の部類です。

## 罠 その 5：Nagging（しつこい引き止め）

> [12] ポップアップで、スタッフにチャットでの相談を促される。**するわけないだろ！**

> [13] これからの流れをもういちど説明される。**さっき見たよ！ 一言一句同じやつ見たよ！**

### 何が起きているか

Nagging です。同じ確認・同じ提案を繰り返して、ユーザーの意志が折れるのを待つ。

特に [13] の「一言一句同じ説明が 2 回出る」は、意図的というより**実装事故**の匂いがします。

### たぶんこういう実装

```tsx
// ステップ定義が複数箇所にある
const STEPS = [
  "reason",
  "offer",
  "pause",
  "explain",     // ← ここ
  "chatOffer",
  "explain",     // ← と、ここ
  "password",
  "done",
];
```

フローに機能を継ぎ足していくうちに、`explain` ステップが 2 回登場するようになった。個別ステップのユニットテストは全部通る。**E2E テストが存在しないので誰も気づかない。**

サブスクの解約フローは、たいてい**プロダクトのなかで最もテストが薄いパス**です。だって PdM も QA も、そこを何度も通りたくないですからね。気持ちはわかる。わかるけど、そのせいで「同じ画面が 2 回出る」が本番で何ヶ月も生き残る。

### どうすれば良かったか

**フローを宣言的な状態機械として 1 箇所に持ち、それに対してテストを書く。**

```ts
import { createMachine } from "xstate";

export const cancelFlow = createMachine({
  id: "cancel",
  initial: "confirm",
  states: {
    confirm:  { on: { NEXT: "reason" } },
    reason:   { on: { NEXT: "summary" } },
    summary:  { on: { CONFIRM: "done", ABORT: "aborted" } },
    done:     { type: "final" },
    aborted:  { type: "final" },
  },
});
```

こうしておくと、こういうテストが書けます。

```ts
test("解約フローに同じ画面は二度出ない", () => {
  const path = shortestPath(cancelFlow, "done");
  expect(new Set(path).size).toBe(path.length);
});

test("解約は3画面以内で完了する", () => {
  expect(shortestPath(cancelFlow, "done").length).toBeLessThanOrEqual(3);
});
```

下のテスト、**わりと本気でおすすめです。**

「解約は N クリック以内」を CI で守る。これがあれば、リテンション施策を 1 つ足すたびにテストが赤くなり、**「引き止め画面を足すなら、既存の画面をどれか削る」という交渉が発生する**。無限に足せなくなるのが大事なんです。予算制約があるから設計が生まれる。

## 罠 その 6：Roach Motel（パスワード再設定で全ロールバック）

> [14] 「念のため」みたいな雰囲気でパスワードを要求されるので入力する。ちなみに、入会時にはそんなステップはない。**入会にも念を入れなさいよ！**

> [15] パスワードを忘れて「再設定用 URL を送信」を押した場合、なぜかポップアップではなく同タブ内で画面が遷移し、**解約手続きがキャンセルされ、「戻る」で戻っても最初からやり直しになる**。**親切の皮を被った巧妙すぎる罠。**

### 何が起きているか

Roach Motel（ゴキブリホイホイ）の教科書的な例です。**入るのは簡単、出るのは難しい。**

そして技術的に見ると、ここには 2 つの独立した問題があります。

**問題 1：認証の非対称性。** 入会にパスワード不要で、解約にパスワード必要。これは「セキュリティ上の理由」で説明されがちですが、成立していません。もし「本人以外による解約」を防ぎたいなら、**「本人以外による課金開始」も同じくらい防ぐべき**でしょう。防いでいないということは、守りたいのは**ユーザーの財産ではない**ということです。

**問題 2：状態管理の設計ミス。** これがエンジニア的にいちばん痛い。

```tsx
// フローの進捗をサーバー側セッションに持っている
// 別ページに遷移した瞬間に破棄される
<a href="/password/reset">再設定用URLを送信</a>
```

パスワード再設定は**別の認証コンテキスト**なので、遷移した時点で解約セッションが破棄される。ブラウザバックしても復元されない。15 ステップ分の進捗が消える。

これ、悪意ではなく**設計の怠慢**である可能性が高いです。ただ、結果として企業が得をして、ユーザーが損をする。前述の判定式に完全に一致します。**悪意がなくてもダークパターンは成立する。** 動機ではなく、**非対称性**が定義なので。

### どうすれば良かったか

**再認証は、フローを離脱させずに行う。**

```tsx
// ❌ ページ遷移でフローが死ぬ
<a href="/password/reset">パスワードを再設定</a>

// ✅ モーダル内で完結し、フローの状態は保持される
<ReauthDialog
  onSuccess={() => flow.send("VERIFIED")}
  onPasswordReset={() => {
    flow.persist();              // 進捗をサーバーに保存
    openInNewTab("/password/reset");
  }}
/>
```

そして根本的には、**フローの進捗は復元可能であるべき**です。

```ts
// 進捗をサーバーに永続化し、いつでも再開できるようにする
POST /api/cancellation-drafts   → { draftId, step: "summary", expiresAt }
GET  /api/cancellation-drafts/:id
```

こうしておけば、途中でブラウザが落ちても、電池が切れても、パスワードを忘れて泣きながら再設定しても、**「続きから」で戻ってこられる**。

ここで大事な観点をひとつ。**わたしたちはこの実装をすでに知っています。**

カート放棄対策のドラフト保存、フォームの自動保存、途中離脱ユーザーへのリマインドメール。**購入フローには全部入っている**んですよ。技術的難易度はゼロです。ライブラリもある。社内に実装例もある。

なのに解約フローには入っていない。**技術的制約ではなく、優先順位の表明**です。そしてコードは、優先順位を正直に記録してしまう。**Git は嘘をつかない。**

## エンジニアのための実務チェックリスト

ここまでの話を、レビューで使える形にまとめます。

**設計レビューで聞くべきこと**

- [ ] このフローの**最短クリック数**は？ 入会フローの何倍？
- [ ] 同じ意味のボタンの色は、**全画面で一貫**しているか？
- [ ] ボタンのラベルを画面から切り離して読んで、**結果がわかる**か？
- [ ] ユーザーが**押し間違えたときに得をするのは誰**か？
- [ ] 追加で発生する金額は、**確定ボタンより前**に円で出ているか？
- [ ] フローの途中で**離脱しても再開**できるか？
- [ ] 入会と解約で、**要求する認証レベルが同じ**か？

**CI で機械的に守れること**

- [ ] 解約フローの最短経路が N ステップ以内（状態機械のテスト）
- [ ] 同じステップが 2 回出現しない
- [ ] 本文テキストのコントラスト比が 4.5 以上
- [ ] フロー内のボタンは `intent` 必須、`variant` 直指定は型エラー

とくに最後の 2 つは、**今日から入れられます。** ダークパターンを撲滅することはできませんが、**うっかりダークパターンになる**のは防げます。世に出ているダークパターンの、おそらく半分くらいは「うっかり」です。半分は「わざと」ですが。

## 結論

長々と書いてきましたが、まとめます。

**ダークパターンは、悪人が作るものではありません。**

デザインシステムを正しく使い、契約条項を忠実に実装し、A/B テストで有意差を確認し、レビューを通し、KPI を達成した**善良なエンジニアたち**が、それぞれのファイルのなかで正しい仕事をした結果、**誰も見ていない全体像がゴキブリホイホイになる**。

各コンポーネントは正しい。各 PR は正しい。各 KPI は達成されている。**統合されたときだけ邪悪。**

これ、要するに**マイクロサービスの分散トランザクションと同じ構造**なんですよ。個々のサービスは整合しているのに、全体としては不整合。違いは、こっちの不整合を踏むのが**サーバーではなく人間**だというところだけです。

そして、この記事でいちばん言いたいことはこれです。

**あなたのプロダクトの解約フローを、あなた自身が最後に通ったのはいつですか？**

入会フローは全員が通ります。デモで見せるから、投資家に見せるから、朝会で共有するから、Lighthouse スコアを測るから。

解約フローは誰も通りません。誰も見ないので、罠が 6 つに増えても誰も気づかない。**風来のシレンだったらフロア入った瞬間に気づくレベルの罠密度**なのに、誰も気づかない。

だから今日、自社のプロダクトを解約してみてください。何クリックかかりましたか。

**16 クリックを超えたら、あなたはもう罠を仕掛ける側です。**

……まあ、ただ。

DAZN の名誉のために書いておくと、元記事の著者もこう締めています。

> でもワールドカップはとても楽しかったよ。それはありがとう。

いい記事だな。わたしたちも、こういうエンジニアでありたいですね。

**解約フローに 30 日のアディショナルタイムを設定しない側の。**
